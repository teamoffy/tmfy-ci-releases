# Per-cloud Kubernetes targets — one line per cloud:
#
#   <stack> k8s <minor|latest>
#
# Each cloud declares the Kubernetes version it wants to run: an explicit
# minor (e.g. 1.37) to hold it back deliberately, or `latest` for the newest
# minor k3s publishes. Everything else is computed, not pinned: check.sh
# resolves the newest k3s patch of that minor plus every component in
# oci-images.txt from its source and <k8s> rule. If a component cannot
# supply the target minor (e.g. no cloud CCM image for it yet), the whole
# cloud drops one minor and resolution retries — `latest` therefore means
# "as new as this cloud's slowest dependency allows", and a cloud moves up
# automatically as soon as every coupled component has a matching version.
# Coupled components today:
#
#   cilium               newest release whose e2e-tested k8s set includes
#                        the minor (operator/envoy follow it)
#   gcp-ccm              same k8s minor (k8s 1.36 -> v36.x)
#   alicloud-csi-plugin  same k8s minor (k8s 1.37 -> v1.37.x)
#   oci-ccm              at most one minor behind
#
# The resolved set is published as a content-addressed `stacks/v<hash>`
# release with a `stacks.txt` asset: one `<stack> <product> <version>`
# row per deployed version, the format consumers read. This file only
# declares intent.

# --------------------------------------------------------------- upcloud
upcloud k8s latest
# -------------------------------------------------------------------- gcp
gcp k8s latest
# -------------------------------------------------------------- alicloud
alicloud k8s latest
# ------------------------------------------------------------------ oci
oci k8s latest
